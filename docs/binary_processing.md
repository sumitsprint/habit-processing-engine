# Purpose

The binary processing pipeline processes binary habits exported from the loop habit tracker app.
Binary habits are habits where the user either performs or does not perform the habit during a
scheduled period, such as meditating every day or completing a workout every 7 days.

the purpose of this pipeline is to process the binary habit data

## Exported Data

A binary habit exported from the Loop Habit Tracker can contain five possible states:

- **YES_MANUAL** – The user marked the habit as completed.
- **NO** – The user marked the habit as not completed.
- **SKIP** – The user intentionally skipped the habit.
- **UNKNOWN** – No information is available for that day.
- **YES_AUTO** – Automatically generated by the application. This state occurs only for habits with a recurrence greater than
  one day and is generated after a `YES_MANUAL` entry.

## Semantic Interpretation of States

The exported states are interpreted using the following semantics.

| State      | Interpretation                                                           |
| ---------- | ------------------------------------------------------------------------ |
| YES_MANUAL | User was expected to perform the habit and succeeded.                    |
| NO         | User was expected to perform the habit but did not.                      |
| SKIP       | User was expected to perform the habit but intentionally abstained.      |
| UNKNOWN    | User was expected to perform the habit, but no information is available. |
| YES_AUTO   | User was not expected to perform the habit on that day.                  |

## State Categories

### Engagement Entries

Engagement entries represent explicit user interactions with the habit. They include:

- YES_MANUAL
- NO
- SKIP

### Active Entries

Active entries represent decisive outcomes. They include:

- YES_MANUAL
- NO

## Design Decisions

`YES_AUTO` is generated by the application rather than by the user. Therefore, wherever a `YES_AUTO` entry occurs, we can infer with complete certainty that the user was not expected to perform the habit on that day.

This leads to another semantic interpretation, which forms the basis of the timeline reconstruction process: every `YES_AUTO` entry represents a non-scheduled day, while all remaining days are considered scheduled days.

**Non-scheduled day** – The user was not expected to perform the habit on that day and is represented by `YES_AUTO`.

**Scheduled day** – The user was expected to perform the habit on that day and is represented by all non-`YES_AUTO` entries.

The goal of the reconstruction process is to produce a timeline that is fully consistent with these semantics.

The semantic interpretation used by this pipeline was inspired by the workout routine.

For example, if a workout is scheduled every Monday, Monday is the only opportunity to perform that workout. Missing it on Monday does not shift the opportunity to Tuesday; the next opportunity is the following Monday.

This behavioral assumption motivated the semantic interpretation adopted by this pipeline.

### Why is timeline reconstruction necessary?

The exported dataset may be sparse. It may contain missing calendar dates and only the days on which the user recorded an entry. Furthermore, `YES_AUTO` entries are generated by the application only after a `YES_MANUAL` entry and are not generated following `NO` or `SKIP`.

However, according to the semantics adopted by this pipeline, every non-scheduled day should be represented by a `YES_AUTO` entry. Therefore, the exported dataset cannot be used directly. The timeline must first be reconstructed so that every day can be classified as either a scheduled day or a non-scheduled day. This allows `YES_AUTO` to be assigned consistently to every non-scheduled day while preserving the user-recorded entries on every scheduled day.

## Processing Pipeline

The binary processing pipeline reconstructs the exported dataset into a complete timeline that is consistent with the semantic model described above. The reconstruction process consists of the following steps.

### Step 1 – Remove `YES_AUTO`

The first step is to remove all `YES_AUTO` entries from the exported dataset.

According to the semantic model adopted by this pipeline, `YES_AUTO` represents every non-scheduled day. However, the Loop Habit Tracker generates `YES_AUTO` only after a `YES_MANUAL` entry and does not generate it following `NO` or `SKIP`. As a result, the exported `YES_AUTO` entries do not consistently represent all non-scheduled days.

Therefore, all `YES_AUTO` entries are removed before timeline reconstruction. During reconstruction, `YES_AUTO` is regenerated consistently according to the semantic model adopted by this pipeline.

### Step 2 – Reconstruct the Timeline

After removing all `YES_AUTO` entries, the pipeline reconstructs the exported dataset into a complete daily timeline.

The exported dataset may be sparse and can contain missing calendar dates. Therefore, a continuous sequence of dates is generated from the earliest to the latest recorded date. Newly created dates are initially assigned the `UNKNOWN` state. At this stage, `UNKNOWN` simply represents missing information and does not imply whether the day is scheduled or non-scheduled.

...

### Anchor Logic

The timeline reconstruction process uses an anchor-based approach to identify scheduled and non-scheduled days.

The frequency denominator from the metadata represents the fixed interval at which the user is expected to perform the habit. The first engagement entry is used as the initial anchor because the exported dataset may contain leading `UNKNOWN` entries, which do not indicate when the user actually started interacting with the habit. Therefore, the first engagement entry provides the earliest reliable reference point from which the schedule can be reconstructed.

Starting from the initial anchor, the pipeline traverses the timeline and computes the number of days elapsed since the current anchor. If the elapsed number of days is divisible by the frequency denominator, the day is classified as a scheduled day, and its existing state is preserved.

If the elapsed number of days is not divisible by the frequency denominator, the day is classified as a non-scheduled day and is assigned the `YES_AUTO` state, consistent with the semantic model adopted by the pipeline.

If an engagement entry appears on a non-scheduled day according to the current anchor, the pipeline interprets this as a change in the user's routine. In this case, the engagement entry becomes the new anchor, and the traversal continues using the same logic with the updated anchor.

By repeating this process until the end of the timeline, the pipeline reconstructs a complete timeline that is fully consistent with the adopted semantic model.

## State Views

Once the timeline has been reconstructed, the pipeline derives multiple state views from it. Each view represents a subset of the timeline based on the semantic interpretation adopted by the pipeline.

The primary state views are:

- **Scheduled View** – Contains all scheduled days.
- **Engagement View** – Contains all engagement entries (`YES_MANUAL`, `NO`, and `SKIP`).
- **Active View** – Contains all active entries (`YES_MANUAL` and `NO`).

These state views simplify downstream processing by allowing performance metrics and behavioral context to be computed without repeatedly filtering the reconstructed timeline.

## Output

The reconstructed timeline and its derived state views are used to compute:

- Performance metrics
- Behavioral context
- Additional behavioral analyses
